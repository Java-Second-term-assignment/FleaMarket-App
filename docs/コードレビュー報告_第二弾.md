# コードレビュー報告 第二弾（第一弾以外の観点）

第一弾（`コードレビュー報告.md`）で扱った内容以外の観点で追加調査した結果です。

- **第一弾で扱ったもの:** CSRF、JWT フィルタ、Stripe Webhook 認証・署名、オープンリダイレクト、Order/User の null チェック、S3 URL、StripeWebhookHandler の UUID、ImageValidator など
- **第二弾で扱うもの:** バリデーション論理、セッション・Cookie、CORS、テンプレートの出力、管理者入力の長さ制限、その他の null やロジック

## 1. バリデーション・論理バグ

### 1.1 RegisterForm.isPasswordMatch() の論理逆転（要修正）

**場所:** `auth/controller/dto/RegisterForm.java`

```java
@AssertTrue(message = "パスワードとパスワード確認が一致しません")
public boolean isPasswordMatch() {
    return password == null || confirmPassword == null || password.equals(confirmPassword);
}
```

- **問題:** 「一致しているとき true」にすべきところ、**password または confirmPassword が null のときも true** になっています。正しくは「両方非 null かつ等しいときのみ true」にすべきです。
- **影響:** `@NotBlank` があるため通常は null で通らないが、API 直接呼び出しや将来の変更で null が渡ると「一致している」と誤判定される可能性があります。
- **推奨:**  
  `return password != null && confirmPassword != null && password.equals(confirmPassword);`

## 2. Null チェック・NPE（第一弾で未対応分）

### 2.1 ReviewService.submitReview の orderEntity.getStatus()

**場所:** `transaction/service/ReviewService.java`

```java
Order order = new Order(
    ...
    OrderStatus.valueOf(orderEntity.getStatus()));
```

- **問題:** 第一弾で `OrderService.toDomain` と `OrderQueryService.getOrderDetail` には status の null ガードを入れましたが、**ReviewService では未対応**です。`orderEntity.getStatus()` が null だと `OrderStatus.valueOf(null)` で NPE になります。
- **推奨:** `orderEntity.getStatus() == null` のときは `IllegalStateException` または `ValidationBusinessException` を投げるか、第一弾と同様にガードを追加してください。

## 3. セッション・Cookie 設定

### 3.1 セッション Cookie の httpOnly / secure が未設定

**場所:** `application.properties` および `SecurityConfig`

- **状況:** `server.servlet.session.*` や Cookie の `httpOnly`・`secure`・`sameSite` の明示的な設定が見当たりません。Spring Boot のデフォルトではセッション Cookie は httpOnly になりますが、本番では **secure（HTTPS のみ）** と **sameSite** の明示を推奨します。
- **推奨:**  
  - 本番用プロファイルで例:  
    `server.servlet.session.cookie.secure=true`  
    `server.servlet.session.cookie.same-site=strict`（または lax）  
  - 必要に応じて `server.servlet.session.timeout` も設定してください。

## 4. CORS 設定

### 4.1 allowCredentials(true) とオリジンリスト

**場所:** `config/cors/CorsConfig.java`

- **状況:** `setAllowCredentials(true)` で、`allowedOrigins` に `http://localhost:3000` と `http://example.com` を指定しています。オリジンが固定なら問題ありませんが、**本番で `*` や過度に広いオリジンと組み合わせると**、他サイトから Cookie 付きで API を呼ばれるリスクがあります。
- **推奨:** 本番では必ず許可するオリジンを列挙し、`*` は使わないでください。現状の列挙型のままでよいです。

## 5. テンプレート（Thymeleaf）の出力

### 5.1 管理者ダッシュボードの [(${...})]（無害だが注意）

**場所:** `templates/admin/dashboard.html`

```html
<script type="application/json" id="itemStatusCountsJson" th:inline="text">[(${itemStatusCountsJson})]</script>
```

- **状況:** `[(${...})]` は Thymeleaf の**エスケープなし**出力です。ただし `itemStatusCountsJson` 等は **ObjectMapper.writeValueAsString()** で生成された JSON のため、改行や引用符は正しくエスケープされています。管理者向けの数値・集計データが中心で、現状の実装で XSS の危険は低いです。
- **推奨:** 今後、ユーザー入力や商品名などを JSON に含める場合は、**必ず ObjectMapper 等でシリアライズ**し、文字列連結で JSON を組み立てないようにしてください。

### 5.2 user_settings の [[${user.caption}]]

**場所:** `templates/user/user_settings.html`

```html
<textarea ...>[[${user.caption}]]</textarea>
```

- **状況:** Thymeleaf の `[[${...}]]` は**エスケープあり**のため、`<script>` 等はそのまま出力されず安全です。`th:text` と同様に扱って問題ありません。

## 6. 管理者操作の入力長

### 6.1 管理画面のユーザー更新（displayName / email）

**場所:** `AdminPageController.usersUpdate`  
`@RequestParam("name") String displayName`, `@RequestParam("email") String email`

- **状況:** 管理者がユーザーの表示名・メールを更新する際、**長さのサーバー側バリデーションがありません**。DB のカラム長（例: display_name 50、email 255）を超える文字列を送ると、DB エラーや切り捨てで不整合になる可能性があります。
- **推奨:** `@Size(max = 50)` などを付与するか、サービス層で長さチェックを行い、超過時は `ValidationBusinessException` で 400 を返すようにすると安全です。

## 7. リポジトリ・クエリ

### 7.1 JPQL / Native クエリ（問題なし）

- **状況:** `ItemRepository`、`AuthUserRepository`、`ItemViewRepository` 等を確認しましたが、クエリはすべて **`:param` によるバインド変数**で、ユーザー入力を文字列連結している箇所はありませんでした。SQL/JPQL インジェクションの心配は不要です。

### 7.2 Pageable / Sort（問題なし）

- **状況:** `ProductListService.createPageRequest` では、リクエストの `sort` を **"low_price" / "popular" / "new" 等の固定値にマッピング**してから `Sort.by(...)` に渡しており、任意のプロパティ名がそのまま Sort に流れていません。インジェクションのリスクはありません。

## 12. まとめ（第二弾）

- **論理バグ:** 登録フォームの「パスワード一致」判定が、null のときに true になってしまうため修正を推奨します。
- **Null 対策:** ReviewService の Order 変換でも status の null ガードを入れると、第一弾と一貫して安全になります。
- **セキュリティ:** セッション Cookie の本番向け設定（secure / sameSite）と、管理画面の入力長制限は、運用が固まってからでよいので低優先で対応可能です。
- **テンプレート・クエリ:** 今回確認した範囲では、XSS や SQL インジェクションの不備はありませんでした。

第一弾とあわせて対応すると、堅牢性と一貫性がさらに高まります。
