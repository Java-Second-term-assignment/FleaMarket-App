## 2. アーキテクチャ・設計

### 良い点

- **パッケージ構成**: `admin` / `auth` / `catalog` / `listing` / `transaction` / `user` / `engagement` など機能単位で分かれており、責務が把握しやすい。
- **ドメインと永続化の分離**: `Order`（ドメイン）と `OrderEntity`（JPA）、`Listing` と DB の分離により、状態遷移ルールがドメインに集約されている（`Order#confirmPurchase()`, `ship()`, `complete()`, `cancel()` など）。
- **共通基盤**: `BusinessException` 系・`ErrorCode`・`GlobalExceptionHandler` により、エラー契約とHTTPステータス・i18nが一貫している。
- **外部連携の抽象化**: `ComprehendClientPort` / `RekognitionClientPort` / `FraudDetectorClientPort` など Port インターフェースで差し替え可能。
- **認証の二系統**: 管理者フォームログイン（`/admin/login`）と一般ユーザー（Webフォーム + API用JWT）が `@Order` 付きの別 `SecurityFilterChain` で分離されており、設計が明確。

### 改善推奨

- **README と実装の齟齬**: README に「Row Level Security (RLS) 実装済み」とあるが、`V1__init.sql` に RLS/ポリシー定義は見当たらない。RLS を実装するか、README の記述を修正することを推奨。
- **API レスポンス形式の統一**: `ApiResponse<T>` がある一方、`UserController#getMe()` などは `ResponseEntity.ok(body)` でラップしていない。フロント・クライアントの期待に合わせて `success/data` 形式を統一するか、意図的に分けている旨をコメントで明示するとよい。
- **Controller の二重化**: `ListingController`（API）と `ListingPageController`（Web）など、API と Web で Controller が分かれているのは良いが、サービス層の再利用ができているか、重複ロジックがないか定期的に確認するとよい。

## 3. セキュリティ

### 良い点

- **認証・認可**
  - JWT は `JwtAuthenticationFilter` で Bearer トークンのみ処理し、失敗時は 401 JSON で返却。
  - パスワードは `BCryptPasswordEncoder` を使用。
  - 管理者と一般ユーザーでログインエントリーポイントを分離し、管理者は `is_admin` チェックで 403 を返す設計。
- **CSRF**: Web チェーンでは CSRF 有効。`/webhooks/**` のみ署名検証で信頼するため除外しており、妥当。
- **オープンリダイレクト対策**: 未認証時の `returnUrl` について「`/` 始まりかつ `//` で始まらない」ことをチェックし、相対パスのみ許可している。
- **入力のエスケープ**: `order_detail.js` のチャット表示で `escapeHtml()` により XSS 対策がされている。
- **権限チェック**: `OrderService` で `order.assertBuyer(currentUserId)` などドメイン側で参加者チェックを実施。

### 改善推奨

- **JWT 秘密鍵**: `application.properties` のデフォルト `app.jwt.secret` は開発用と明示し、本番では必ず環境変数 `APP_JWT_SECRET` で 256bit 以上を設定する運用を README やデプロイ手順に明記するとよい。
- **GlobalExceptionHandler のスコープ**: `BusinessException` のみハンドリングし、その他は Spring デフォルトに委譲する方針はコメントで説明されている。一方で、本番では `Throwable` 用のフォールバックで 500 と汎用メッセージを返し、スタックトレースをログのみに留める実装も検討の価値あり（情報漏洩防止）。
- **ログへの機密情報**: パスワードやトークンがログに出力されないよう、すでに配慮されているが、`request.getParameter("password")` などを `log.debug` に渡さないようレビュー観点として維持するとよい。
- **Stripe Webhook**: 署名検証（`StripeWebhookVerifier`）で未設定時は適切にエラーにしており、良い。

## 4. コード品質・保守性

### 良い点

- **例外設計**: `NotFoundBusinessException`, `ValidationBusinessException`, `AccessDeniedBusinessException` など `ErrorCode` と紐づいたビジネス例外が揃っている。
- **バリデーション**: API では `@Valid` / `@Validated`、`@Size` / `@Email` / `@NotBlank` を DTO に使用。掲示板の `@Size(max = 1000)` など制約が明示されている。
- **ネイティブクエリ**: `ItemRepository` の `countItemsByDaySince` などは `:since` でパラメータバインドしており、SQL インジェクションの心配は低い。
- **ドキュメント**: `ErrorCode` の Javadoc、`GlobalExceptionHandler` の「Accept に応じて HTML/JSON を返す」説明など、意図が読み取りやすい。

### 改善推奨

- **API と Web のバリデーション統一**: フォーム（Thymeleaf）と API で同じ項目の制約（例: 表示名の最大長）が重複している場合、共通のアノテーションや定数に寄せると変更漏れを防げる。
- **マジックナンバー**: 例: `order_detail.js` の `size=50` などは定数化すると意図が明確になる。
- **null 安全**: `OrderService#createOrderFromProduct` の `item.getPriceAmount() != null ? ... : 0L` のように null を考慮しているが、ドメインや DTO で `Optional` やプリミティブで表現できる箇所は検討の余地あり。

## 5. テスト

### 良い点

- **統合テスト基盤**: `IntegrationTestBase` で Testcontainers（PostgreSQL）、S3/Comprehend/Rekognition のモック、JWT 取得ヘルパー（`obtainAccessToken`, `authHeaders`）が用意されている。
- **ドメインテスト**: `OrderTest`, `OrderStatusTest`, `ListingTest`, `UserTest` などドメインロジックの単体テストがある。
- **サービス単体テスト**: `OrderServiceTest`, `ChatServiceTest`, `UserServiceTest` など、主要サービスにテストが存在する。
- **認証・決済の統合テスト**: `AuthIntegrationTests`, `StripeWebhookIntegrationTests` で重要な経路がカバーされている。

### 改善推奨

- **テスト依存関係**: `pom.xml` の `spring-boot-starter-data-jpa-test`, `spring-boot-starter-thymeleaf-test`, `spring-boot-starter-validation-test`, `spring-boot-starter-webmvc-test` は Spring Boot 標準の BOM に含まれない可能性がある。実際に `mvn test` が通るか、必要であれば `spring-boot-starter-test` のみに統一するか、公式ドキュメントで artifact 名を確認することを推奨。
- **Controller 単体テスト**: `MockMvc` による API の単体テストが少ない。重要なエンドポイント（認証必須・権限エラー・バリデーションエラー）を数本でも追加すると、リグレッション防止に有効。
- **カバレッジ**: 現状のテストでどこまでカバーされているか、JaCoCo 等で計測し「クリティカルなサービスは ○○% 以上」などの目標を置くとよい。

## 6. パフォーマンス・DB

### 良い点

- **Flyway**: `V1__init.sql`（スキーマ）と `V2__seed.sql`（シード）でマイグレーションが管理されている。
- **スキーマ設計**: PK に UUID、金額は bigint（最小通貨単位）、手数料は bps、`updated_at` はトリガで更新など、一貫した方針。
- **インデックス**: `items(status, created_at DESC)`、`orders(buyer_id, created_at DESC)`、`search_tsv` の GIN、`name` の trigram など、検索・一覧・フルテキスト用のインデックスが設定されている。
- **トランザクション**: 更新系サービスに `@Transactional` が付与されており、単位も適切（1リクエスト＝1トランザクションに近い）。

### 改善推奨

- **N+1**: 一覧取得で `ItemEntity` に紐づく `item_images` や `categories` を取得している場合、`@EntityGraph` や `JOIN FETCH` で N+1 が発生していないか確認するとよい。
- **ページネーション**: 一覧 API で `Pageable` を使っている場合は、`size` の上限（例: 100）を設定すると安全。

## 7. 設定・運用

### 良い点

- **プロファイル**: `spring.profiles.active=${SPRING_PROFILES_ACTIVE:dev}` でデフォルト dev、本番は環境変数で上書きする構成。
- **機密情報**: DB URL・JWT 秘密鍵・Stripe・メール設定など、環境変数で上書きできる形になっており、デフォルトは開発用と分かりやすい。
- **Flyway の場所**: `classpath:db/migration` でマイグレーションが整理されている。テストでは `db/test_migration` を追加できるよう `IntegrationTestBase` で上書きしている。

### 改善推奨

- **pom.xml の Flyway プラグイン**: `flyway-maven-plugin` の `password` が空でハードコードされている。ローカルで `mvn flyway:*` を実行する場合は、`-Dflyway.password=...` やプロファイルで上書きする運用を明記するとよい。
- **README との一致**: 技術スタック（Spring Boot 4.0.1、PostgreSQL、JWT 等）は README と一致している。RLS の記述のみ、上記のとおり修正を推奨。
