# コードレビュー報告（最新）

実施日: 2025年2月6日  
対象: FleaMarket-App コードベース全体

既存の「コードレビュー報告_実務観点.md」で指摘された項目の**現状確認**と、**追加で発見した点**をまとめています。

---

## 1. 総評

### 良い点
- **ドメインとエンティティの分離**（Order, Listing, User 等）ができており、ビジネスルールがドメインに集約されている。
- **ErrorCode + GlobalExceptionHandler** により API のエラー契約が統一されている。
- **OrderStatus.fromString** の null/不正値ガード、**User.requireText** による入力検証がドメイン層で行われている。
- **セキュリティ**: CSRF 有効、Webhook は `/webhooks/**` のみ CSRF 除外、オープンリダイレクト対策（returnUrl の相対パスチェック）、JWT/署名検証の実装あり。
- **トランザクション**: 参照系に `@Transactional(readOnly = true)` が適切に付与されている。
- **RegisterForm.isPasswordMatch()** は現状で正しい実装（両方非 null かつ等しいとき true）。

### 要対応（優先度順）
1. **例外の統一**: `UserService` 等で `IllegalArgumentException` を使用しており、API が 500 を返す原因になっている。
2. **認証パス設計**: `/user/**` が API 用セキュリティチェーンに含まれておらず、JWT で `/user/me` を呼んでもセッション認証が要求される。
3. **CORS**: `/api/**` のみ設定されており、SPA から `/auth/**`・`/user/**` を呼ぶ場合に CORS が効かない。
4. **テスト不足**: 実質的に context load のみで、単体・統合テストがほぼない。
5. **軽微**:  typo（DateTimeUtil）、その他サービス層の例外統一。

## 2. 例外設計・エラーハンドリング

### 2.1 UserService の IllegalArgumentException（要修正）

**場所:** `UserService.java`

| メソッド | 行 | 現状 | 推奨 |
|----------|-----|------|------|
| getRequired | 47 | `IllegalArgumentException("User not found: " + userId)` | `NotFoundBusinessException.of(ResourceType.USER)` |
| updateProfile | 55 | 同上 | 同上 |
| updateAddress | 68 | 同上 | 同上 |
| submitVerification | 119 | 同上 | 同上 |

**影響:** `GlobalExceptionHandler` は `BusinessException` のみハンドリングするため、上記は Spring デフォルトで 500 として返却される。クライアントには 404 で返すべき。

**修正例:**
```java
.orElseThrow(() -> NotFoundBusinessException.of(ResourceType.USER));
```

### 2.2 UserService.updateProfileImage のファイル名・拡張子エラー

**場所:** `UserService.java` 164, 168 行目

- `"Original filename is null or empty"` → **ValidationBusinessException**（例: ErrorCode.INVALID_IMAGE_FORMAT または新規メッセージキー）に統一すると、API で 400 として返せる。
- `"File extension not found"` → 同様に ValidationBusinessException 推奨。

199 行目の `RuntimeException("Failed to read image file", ex)` は、`ExternalServiceException` や既存の IMAGE_UPLOAD_FAILED 系の BusinessException にラップすると、エラー契約が揃う。

### 2.3 その他のサービス層

- **UserRankService** (18行目): `IllegalArgumentException("Rank not found: " + rankId)` → 存在しないランクID は NOT_FOUND 系 BusinessException が妥当。
- **DbAuthUserProvider** (20行目): 認証失敗時の `IllegalArgumentException("not found")` → 認証エラーとして UnauthorizedBusinessException 等に揃えると一貫する。
- **ItemViewService** (56行目): UUID 変換失敗の `IllegalArgumentException` → 不正リクエストなら ValidationBusinessException が自然。

ドメイン層（`User`, `Listing` の requireText / バリデーション）で投げる `IllegalArgumentException` は、コントローラで `@Valid` を徹底して防ぐか、サービス層で catch して ValidationBusinessException に変換する運用でよい。

### 2.4 UserProfileQueryService.getMe

**場所:** `UserProfileQueryService.java` 35 行目

```java
UserEntity entity = userRepository.findById(userId).orElseThrow();
```

直前に `userService.getRequired(userId)` で存在保証しているため実害は小さいが、契約上「存在しない場合」が明示されていない。将来的に getRequired の実装が変わると `NoSuchElementException` がそのまま伝播し 500 になる。  
**推奨:** `orElseThrow(() -> NotFoundBusinessException.of(ResourceType.USER))` に変更するか、取得を 1 回にまとめる。

## 3. セキュリティ・認証

### 3.1 セキュリティフィルタチェーンと /user/** の扱い（要確認）

**現状:**
- **API 用チェーン (Order 2):** `securityMatcher("/api/**", "/auth/**", "/community/**", "/orders/**")` → JWT、stateless。
- **Web 用チェーン (Order 3):** `securityMatcher("/**")` → フォームログイン、セッション。

`UserController` は `@RequestMapping("/user")` のため、エンドポイントは `/user/me`, `/user/me/profile-image` 等。これらは **API 用チェーンのマッチャに含まれていない** ため、実際に適用されるのは **Web 用チェーン**。  
結果として、`AuthorizationConfig.configureApi()` 内の `.requestMatchers("/user/me/**").hasRole("USER")` は **参照されていない**。SPA が JWT のみで `GET /user/me` を呼ぶと、セッション認証が要求され、JWT だけでは 401 またはログインリダイレクトになる可能性がある。

**推奨:**
- **A:** JWT で保護したいユーザー API を使う場合、API 用チェーンの `securityMatcher` に **`"/user/**"` を追加**する。
- **B:** または `UserController` のベースパスを **`/api/user`** に変更し、既存の `/api/**` でカバーする。
- Web（Thymeleaf）のみで `/user/me` を使う意図であれば、その旨をコメントまたはドキュメントで明示するとよい。

### 3.2 CORS の適用範囲

**場所:** `CorsConfig.java`

```java
source.registerCorsConfiguration("/api/**", config);
```

設定が **`/api/**` のみ**。同一オリジン以外のフロント（例: localhost:3000）から `Authorization: Bearer` で `/auth/**`（ログイン・リフレッシュ）や `/user/**` を呼ぶ場合、**CORS が適用されずブラウザでブロック**される可能性がある。

**推奨:** SPA から呼ぶパスをすべてカバーするよう、`/api/**`, `/auth/**`, `/user/**`, `/orders/**` 等に同じ CORS 設定を追加するか、`/**` で共通設定を適用する。

## 4. トランザクション・一貫性

- **読み取り専用:** `OrderQueryService`, `ItemQueryServiceImpl`, `ProductListService`, `UserProfileQueryService` 等で `@Transactional(readOnly = true)` が適切に使用されている。
- **ListingServiceImpl.createItem:** 商品作成 → 画像アップロード → AI モデレーションの順。画像アップロード後にモデレーションで例外が出ても、商品と画像は永続化済みで、DB 分のみロールバック。ドキュメントの「違反時のみ DB に記録、出品は成功させる」方針と一致している。画像アップロード失敗時は商品も作成しない仕様であれば、トランザクション境界と S3 ロールバック（削除）の検討が必要。

## 5. その他の指摘

### 5.1 Typo

**場所:** `DateTimeUtil.java` 28 行目

```java
throw new IllegalArgumentException("Clock ust not be null");
```

→ **"ust"** を **"must"** に修正。

### 5.2 テスト

**現状:** `FleaMarketAppApplicationTests` の context load のみ。単体・統合テストがほぼない。

**推奨（優先度の例）:**
1. 単体: ドメイン（Order の状態遷移等）、主要サービス（OrderService, UserService の主要シナリオ）、例外（OrderStatus.fromString, StripeWebhookVerifier の署名失敗等）。
2. 統合: 認証（ログイン → トークン取得 → 保護 API 呼び出し）、注文フロー、Webhook（署名あり/なし・不正 payload で期待どおり 400/401/503）。

### 5.3 pom.xml

- Spring Boot 4.0.1、Java 17、Flyway、Testcontainers 等の構成は妥当。`spring-boot-starter-data-jpa-test` 等のテスト用スターターは Spring Boot 4 で利用可能なことを確認済み。
- Flyway の `dev_migration` を本番で読み込まないよう、プロファイルで `spring.flyway.locations` を切り替えているかは運用で確認するとよい。

## 7. 既存報告との対応

- **強み:** ドメイン分離、エラーコード・例外の設計方針、セキュリティの意識は実務レベルで十分。OrderStatus / User の防御的プログラミングも良い。
