# コード品質調査（その他観点）

実施日: 2025年2月6日  
対象: FleaMarket-App コードベース

既存の「コードレビュー報告_最新.md」および「実装されていない機能の詳細調査.md」で扱っていない観点から、問題点を調査・まとめたドキュメントです。

---

## 1. データ整合性・ビジネスロジック

### 1.1 商品ステータスを SOLD に更新していない（重要）

**場所:** `OrderService.createOrderFromProduct()`

**現状:** 注文作成時に `orderRepository.save(e)` で注文を保存するが、**`items.status` を `SOLD` に更新する処理が存在しない**。

**影響:**
- 購入済み商品が一覧で「売り切れ」バッジを表示しない（`ProductListService` は `item.getStatus()` が SOLD の場合にのみバッジ表示）
- 購入済み商品が引き続き検索結果に表示され、カートに追加可能な状態に見える
- 商品詳細では `STATUS_PUBLISHED` または `SOLD` の両方で表示するため、購入後も商品ページは表示されるが、状態の不整合が発生

**推奨対応:**
```java
// createOrderFromProduct 内で注文保存後
itemRepository.updateStatus(itemId, ItemStatus.SOLD.name());
```

※ `ItemRepository` には既に `updateStatus(itemId, status)` が定義済み。注文作成と同一トランザクション内で実行すること。

---

### 1.2 LISTING_ALREADY_SOLD が未使用・重複購入時のエラー表現

**場所:** `ErrorCode.LISTING_ALREADY_SOLD`、`OrderService.createOrderFromProduct()`

**現状:**
- `LISTING_ALREADY_SOLD` は定義されているが、どこからも `throw` されていない
- 既に注文が存在する商品（`orders.item_id` は UNIQUE）に対して再度注文を作成しようとすると、`DataIntegrityViolationException` が発生し、500 として返却される

**影響:** ユーザーには「既に売り切れです」ではなくサーバーエラーとして表示される。

**推奨対応:**
- 注文作成前に、対象商品の `status` が PUBLISHED であること、および既に該当 item_id の注文が存在しないことをチェックする
- 売り切れ・既購入の場合は `ValidationBusinessException`（`LISTING_ALREADY_SOLD`）を投げて 400 で返す
- あわせて 1.1 の通り、注文作成時に item を SOLD に更新する

## 2. パフォーマンス

### 2.1 サムネイル画像取得の N+1 クエリ

**場所:**
- `ProductListService.toProductListDtos()` / `toProductListViewDto()` … 商品一覧の各アイテムで `itemImageService.getThumbnailImageUrl(item.getId())` を呼び出し
- `ProductListService.getRankings()` … `toRankingDto()` 内で同様
- `OrderQueryService.toListItemDto()` … 注文ごとに `itemImageService.getThumbnailImageUrl(e.getItemId())` を呼び出し
- `UserProductsQueryService.toDto()` … 商品ごとに `itemImageService.getThumbnailImageUrl(item.getId())` を呼び出し

**現状:** `ItemImageService` には `getThumbnailImageUrl(UUID itemId)` のみ存在し、複数 itemId を一括取得するメソッドがない。そのため、一覧表示時に item 数分の DB アクセスが発生する（N+1 パターン）。

**推奨対応:**
- `ItemImageService` に `Map<UUID, String> getThumbnailImageUrls(Collection<UUID> itemIds)` のようなバッチメソッドを追加
- 一覧用 DTO 変換の前に itemIds を収集し、1 回のクエリで全サムネイル URL を取得してからマッピングする

---

### 2.2 メモリ内での件数制限（UserProductsQueryService）

**場所:** `UserProductsQueryService.listBySeller()`

**現状:**
```java
List<ItemEntity> items = itemRepository.findBySellerIdAndStatusNotOrderByUpdatedAtDesc(sellerId, STATUS_DELETED);
return items.stream().limit(MAX_ITEMS).map(this::toDto).toList();
```
`findBySellerIdAndStatusNotOrderByUpdatedAtDesc` は `limit` を付けずに全件取得してから、メモリ上で `limit(50)` を適用している。

**影響:** 出品点数が多いユーザーで、不要に多くのレコードを DB から取得する。

**推奨対応:** `ItemRepository` に `Pageable` を受け取るメソッドを追加し、DB レベルで `LIMIT 50` を適用する。

## 3. セキュリティ（既存報告以外）

### 3.1 セキュリティヘッダの未設定

**現状:** `Content-Security-Policy`、`X-Frame-Options`、`X-Content-Type-Options`、`Strict-Transport-Security` などのセキュリティヘッダが明示的に設定されていない。Spring Security のデフォルトで一部は付与される場合があるが、本番環境では明示設定を推奨する。

**推奨対応:**
- `SecurityConfig` や `WebMvcConfig` で `HeadersConfigurer` により以下を設定することを検討:
  - `X-Frame-Options: DENY` または `SAMEORIGIN`
  - `X-Content-Type-Options: nosniff`
  - `Content-Security-Policy`（許可するリソースを制限）
  - 本番では `Strict-Transport-Security`（HTTPS 強制）

---

### 3.2 レート制限の未実装

**現状:** ログイン、パスワードリセット要求、新規登録などのエンドポイントにレート制限がない。

**影響:**
- ブルートフォース攻撃やアカウント列挙のリスク
- パスワードリセットの大量要求によるメール送信の濫用

**推奨対応:**
- Spring の `RateLimiter` や Bucket4j 等を利用したレート制限の導入
- ログイン失敗回数に応じた一時ロックの検討

---

## 4. 入力検証・堅牢性

### 4.1 配送先スナップショットの JSON エスケープ不足

**場所:** `CartService.toJsonSnapshot()`

**現状:**
```java
private static String escapeJson(String s) {
    if (s == null) return "";
    return s.replace("\\", "\\\\").replace("\"", "\\\"");
}
```
バックスラッシュとダブルクォートのみエスケープしている。改行 (`\n`)、タブ (`\t`)、その他の制御文字が含まれる場合、生成される JSON が不正になる、または意図しない解釈を招く可能性がある。

**推奨対応:**
- 正規の JSON ライブラリ（Jackson の `ObjectMapper.writeValueAsString` 等）でシリアライズする
- または、制御文字・改行・タブ等も適切にエスケープするよう `escapeJson` を拡張する

## 5. ロギング・運用

### 5.1 ログのばらつきと重要イベントの監査

**現状:**
- ログは `UserService`、`AdminPageController`、`S3ImageServiceImpl` など一部に限定的に実装されている
- 注文作成、決済完了、パスワード変更、管理者によるユーザー凍結・削除など、監査上重要なイベントのログが不足している箇所がある

**推奨対応:**
- 注文作成・ステータス変更、決済関連、権限変更など重要イベントに構造化ログを追加
- 監査要件に応じて、誰が・いつ・何をしたかを追跡可能にする

---

### 5.2 PII のログ出力

**場所:** `AuthPageController` 73 行目付近

**現状:** `log.info("User registered successfully: email={}", form.getEmail());` でメールアドレスをログに出力している。

**影響:** 個人情報保護の観点で、本番環境では PII をログに含めない運用が望ましい場合がある。

**推奨対応:** メールアドレスをそのまま出力せず、ハッシュやマスクを検討する。または、登録成功のログを DEBUG にし、本番では INFO でメールアドレスを出さないようにする。

---

## 6. 設定・保守性

### 6.1 CORS のオリジンがハードコード

**場所:** `WebMvcConfig.addCorsMappings()`、`CorsConfig`

**現状:** `allowedOrigins("http://localhost:3000", "http://example.com")` のようにオリジンがコード内で固定されている。

**推奨対応:** `application.properties` や環境変数でオリジン一覧を設定し、プロファイルや環境に応じて切り替えられるようにする。

## 7. 推奨アクション一覧（優先度別）

| 優先度 | 観点 | 項目 | 内容 |
|--------|------|------|------|
| 高 | データ整合性 | 商品 SOLD 更新 | `createOrderFromProduct` 内で注文作成後に `itemRepository.updateStatus(itemId, "SOLD")` を呼ぶ |
| 高 | データ整合性 | 売り切れチェック | 注文作成前に item の status と注文の存在を確認し、`LISTING_ALREADY_SOLD` で 400 を返す |
| 中 | パフォーマンス | N+1 解消 | `ItemImageService` にバッチ取得メソッドを追加し、一覧表示で 1 回のクエリにまとめる |
| 中 | パフォーマンス | UserProducts の limit | `ItemRepository` に Pageable 版のメソッドを追加し、DB で件数制限する |
| 中 | 堅牢性 | JSON エスケープ | `CartService.toJsonSnapshot` を Jackson 等で置き換えるか、エスケープを拡張する |
| 中 | セキュリティ | セキュリティヘッダ | CSP、X-Frame-Options 等を明示設定する |
| 低 | セキュリティ | レート制限 | ログイン・パスワードリセット等にレート制限を導入する |
| 低 | 運用 | 監査ログ | 重要イベントにログを追加する |
| 低 | 運用 | PII ログ | メールアドレス等のログ出力を抑制・マスクする |
| 低 | 保守性 | CORS 設定 | オリジンをプロパティ・環境変数で管理する |
