# コードレビュー報告（セキュリティ・nullチェック）

現時点で実装されているコードを対象に、**致命的でないセキュリティ上の懸念**と**nullチェック・防御的プログラミング**の観点でレビューした結果です。

---

## 1. セキュリティ関連

### 1.1 CSRF 無効化（要検討） → **対応済み**

**場所:** `SecurityConfig.java`（3つの `SecurityFilterChain`）

- **対応内容:** フォームベースの Web（管理者ログイン・一般 Web の `/**`）では CSRF を有効（デフォルトのため明示的には無効化していない）。API 用チェーン（`/api/**`, `/auth/**`, `/community/**`, `/orders/**`）のみ `.csrf(AbstractHttpConfigurer::disable)` で無効化し、トークンベース認証に合わせた構成にしている。

---

### 1.2 JWT 認証フィルタが未実装 → **対応済み**

**場所:** `JwtAuthenticationFilter.java`

- **対応内容:** `Authorization: Bearer <token>` から JWT を取得し、`JwtSupport` で署名・有効期限を検証。`UserIdUserDetailsLoader` で principal を組み立て、`SecurityContextHolder.getContext().setAuthentication(...)` で設定するように実装済み。アクセストークンは `TokenService` 経由で `JwtSupport` による真正の JWT 発行に変更済み。

---

### 1.3 Stripe Webhook の認証と署名 null → **対応済み**

**場所:** `SecurityConfig`, `AuthorizationConfig`, `StripeWebhookController.java`, `StripeWebhookVerifier.java`

- **対応内容:**  
  - 問題1: `/webhooks/**` は認可で `permitAll()` 済み。**Web チェーンで CSRF の無視対象に `/webhooks/**` を追加**（`SecurityConfig.webSecurityFilterChain`）し、Stripe の POST が 403 にならないようにした。  
  - 問題2: 署名ヘッダー欠落時はコントローラで既に 400 を返している。  
  - 追加: `StripeWebhookVerifier` で webhookSecret が null/blank のときは検証前に `WEBHOOK_NOT_CONFIGURED`（503）を返すようにした。署名検証失敗時は `WEBHOOK_SIGNATURE_INVALID`（401）を返すようにした。

---

### 1.4 オープンリダイレクト対策（良好）

- **WebLoginSuccessHandler:** `returnUrl` を相対パスまたは同一ホストに限定しており、オープンリダイレクト対策がされています。
- **認証エントリーポイント（SecurityConfig）:** `returnUrl` も相対パスのみ許可する実装になっており問題ありません。

---

### 1.5 管理者ログイン後の権限チェック（良好）

- **AdminLoginSuccessHandler:** 非管理者が管理者ログインURLでログインした場合、セッション破棄して `/admin/login?error=forbidden` にリダイレクトしており適切です。

---

## 2. Null チェック・NPE リスク

### 2.1 Order 関連の `getStatus()` が null の場合

**場所:**  
- `OrderService.toDomain(OrderEntity e)`  
- `OrderQueryService.getOrderDetail(...)` 内の `OrderStatus.valueOf(e.getStatus())`  
- `ReviewService.submitReview(...)` 内の `OrderStatus.valueOf(orderEntity.getStatus())`

```java
Order order = new Order(..., OrderStatus.valueOf(e.getStatus()));
```

- **状況:** DB 上 `status` が nullable だったり、将来のマイグレーションで null が入る可能性がある場合、`valueOf(null)` で **NPE** になります。
- **推奨:**
  - エンティティの `status` を DB で NOT NULL にしている場合は、コメントで明示するとよいです。
  - 防御的にする場合は、`e.getStatus() == null` のときは `NotFoundBusinessException` や `ValidationBusinessException` にし、`valueOf` を try-catch するか、ユーティリティで安全に enum 化する方法があります。

---

### 2.2 OrderQueryService の buyerId / sellerId

**場所:** `OrderQueryService.getOrderDetail`

```java
boolean isBuyer = e.getBuyerId().equals(userId);
boolean isSeller = e.getSellerId().equals(userId);
```

- **状況:** `OrderEntity` では `buyer_id`, `seller_id` は `nullable = false` のため通常は null ではありませんが、既存データや整合性破損時に null だと NPE になります。
- **推奨:** 防御的にするなら `Objects.equals(e.getBuyerId(), userId)` のようにし、`e.getBuyerId() == null` の場合は「注文データ不整合」として 404 や 500 扱いにする方が安全です。

---

### 2.3 SecurityUtil.getCurrentUserId() の UserDetails#getUsername()

**場所:** `SecurityUtil.getCurrentUserId()`

```java
if (auth.getPrincipal() instanceof UserDetails ud) {
    return UUID.fromString(ud.getUsername());  // getUsername() が null の可能性
}
```

- **状況:** 一般的な `UserDetails` 実装では `getUsername()` が null を返さない想定ですが、カスタム実装では null の可能性があります。`UUID.fromString(null)` は NPE です。
- **推奨:**  
  - `UserIdUserDetails` を使っている場合は `username` は `userId.toString()` で保証されているため問題ありません。  
  - 他実装を考慮するなら `String name = ud.getUsername(); if (name == null || name.isBlank()) throw new IllegalStateException("Unauthenticated");` のようにガードすると安全です。

---

### 2.4 UserService.updateProfile の displayName

**場所:** `UserService.updateProfile(UUID userId, String displayName)`

```java
e.setDisplayName(displayName.trim());
```

- **状況:** コントローラで `UpdateProfileRequest` は `@NotBlank` のため通常は null ではありません。ただし別の呼び出し元から `displayName == null` で呼ばれると **NPE** になります。
- **推奨:**  
  - サービス層の契約として「null 禁止」を明示するか、  
  - `displayName == null ? "" : displayName.trim()` のように null 安全にするとよいです。

---

### 2.5 UserService.toDomain の identityStatus

**場所:** `UserService.toDomain(UserEntity e)`

```java
VerificationStatus.valueOf(e.getIdentityStatus())
```

- **状況:** `UserEntity.identityStatus` は `nullable = false` のため通常は null ではありません。既存データ不整合時に null だと NPE です。
- **推奨:** DB 制約で NOT NULL を徹底するか、防御的に `e.getIdentityStatus() == null` の場合はデフォルト値や例外で扱うとよいです。

---

### 2.6 S3ImageServiceImpl.generateImageUrl

**場所:** `S3ImageServiceImpl.generateImageUrl(String bucketName, String s3Key)`

```java
return String.format("https://%s.s3.%s.amazonaws.com/%s", bucketName, region, s3Key);
```

- **状況:** `bucketName` や `s3Key` が null だと URL に `"null"` が入り、不正な URL になります。
- **推奨:**  
  - 呼び出し元で null にしない設計にするか、  
  - メソッド先頭で `Objects.requireNonNull(bucketName);` / `Objects.requireNonNull(s3Key);` で失敗を早めるか、  
  - null の場合は例外を投げるようにするとよいです。

---

### 2.7 StripeWebhookHandler の orderId 形式

**場所:** `StripeWebhookHandler.onWebhook(VerifiedWebhook e)`

```java
if (e.orderId() == null || e.orderId().isBlank()) {
    return;
}
UUID orderId = UUID.fromString(e.orderId());  // 不正な文字列で IllegalArgumentException
```

- **状況:** `orderId` が UUID 形式でない文字列の場合、`UUID.fromString` が **IllegalArgumentException** を投げます。
- **推奨:** try-catch でキャッチし、ログを出して return するか、不正 Webhook としてエラー応答するなど、例外でハンドラが落ちないようにするとよいです。

---

### 2.8 ListingServiceImpl の valueOf

**場所:** `ListingServiceImpl.createItem`

```java
ItemCondition condition = ItemCondition.valueOf(request.getCondition());
ShippingFeePayer shippingFeePayer = ShippingFeePayer.valueOf(request.getShippingFeePayer());
```

- **状況:** `CreateItemRequest` は `@Pattern` で値を制限しているため、通常は不正値は入りません。ただし別経路やバリデーション抜けで不正文字列だと **IllegalArgumentException** になります。
- **推奨:** コントローラで `@Valid` を徹底している限りは問題ありません。サービスを他から呼ぶ場合は、不正値用に catch して `ValidationBusinessException` に変換するのもありです。

---

### 2.9 ItemImageServiceImpl の image.getS3Key()

**場所:** `ItemImageServiceImpl.getItemImageUrls`, `getThumbnailImageUrl`, `deleteItemImages` など

- **状況:** `ItemImageEntity.getS3Key()` が DB 上 NOT NULL であれば通常は null ではありません。null の場合 `generateImageUrl(bucketName, null)` が呼ばれ、上記の S3 URL 生成で `"null"` が混入する可能性があります。
- **推奨:** S3 キーを NOT NULL にしておくか、`getS3Key() == null` の場合はスキップまたは例外にする処理があると安全です。

---

## 3. その他の推奨

### 3.1 UserController.updateProfileImage の image

- **場所:** `UserController.updateProfileImage(@RequestParam("image") MultipartFile image)`
- **状況:** `@RequestParam("image")` は required 未指定のためデフォルトで required=true です。ただしクライアントが空で送ると `image` が空の MultipartFile になる可能性はあり、`UserService.updateProfileImage` 内で `ImageValidator.validate(imageFile, ...)` が null/empty チェックをしているため、実害は小さいです。明示的に `required = true` にすると意図が伝わります。

### 3.2 OrderPageController の orderDetail

- **状況:** `orderQueryService.getOrderDetail(orderId, userId)` は注文が存在しない場合 `NotFoundBusinessException`、権限がない場合 `AccessDeniedBusinessException` を投げるため、null で返すことはありません。問題ありません。

### 3.3 GlobalExceptionHandler

- **状況:** `BusinessException` のみハンドリングし、それ以外は Spring のデフォルトに任せています。NPE や `IllegalArgumentException` は 500 や 400 として返ることになり、本番ではログ・監視で追えるようにしておくとよいです。

---

## 4. 修正優先度の目安

| 優先度 | 項目 |
|--------|------|
| 高     | Stripe Webhook の URL を `permitAll()` にし、署名必須・署名 null チェックを追加する |
| 高     | JWT フィルタを実装するか、使わないなら役割を明記する |
| 中     | Order の `getStatus()` が null の場合の防御（DB NOT NULL 確認 or ガード） |
| 中     | StripeWebhookHandler の `UUID.fromString(e.orderId())` の例外処理 |
| 低     | CSRF を Web フォーム用に有効化する検討 |
| 低     | UserService.updateProfile の displayName null ガード、S3 URL 生成の null チェックなど |

---

## 5. まとめ

- **セキュリティ:** Webhook の認証設定と署名 null、JWT フィルタの未実装が主な懸念です。オープンリダイレクトと管理者ログイン後の権限チェックは適切です。
- **Null チェック:** Order の `status` / buyerId / sellerId、User の displayName / identityStatus、S3 の bucket/key、Webhook の orderId など、**DB や外部入力が null になり得る箇所**で防御的に null チェックや例外ハンドリングを入れると、不整合データや将来の変更に強くなります。
- 致命的な認証バイパスや SQL インジェクションは見当たりませんが、上記を順に対応すると、運用時の障害とセキュリティリスクを減らせます。
