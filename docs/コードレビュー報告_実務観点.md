# コードレビュー報告（実務観点）

実務レベルの観点でコードベースをレビューした結果です。既存の「コードレビュー報告.md」「コードレビュー報告_第二弾.md」で指摘済みの項目は参照のみとし、本ドキュメントでは**アーキテクチャ・トランザクション・例外設計・API設計・テスト・運用**を中心に整理しています。

---

## 1. 総評

- **良い点**
  - ドメイン（Order, Listing 等）とエンティティの分離、ErrorCode と GlobalExceptionHandler による一貫したエラー契約、JWT/Webhook 署名の実装、`@Transactional(readOnly = true)` の適切な使用が多く見られる。
  - 既存レビューで指摘された CSRF/Webhook/JWT/オープンリダイレクト対策は対応済みとされている。

- **実務で特に改善したい点**
  - **例外の統一**: 一部で `IllegalArgumentException` を使用しており、API が 500 を返す原因になっている。
  - **認証・認可のパス設計**: API 用チェーンと `/user/**` のマッチングが噛み合っておらず、JWT で保護したい API がセッション認証になっている可能性がある。
  - **テスト不足**: 単体・統合テストがほぼなく、リグレッションとリファクタの安全性が確保しづらい。
  - **CORS**: 設定が `/api/**` のみで、`/auth/**` や `/user/**` を SPA から呼ぶ場合に CORS が効かない可能性がある。

## 2. アーキテクチャ・設計

### 2.1 パッケージ構成（良好）

- `catalog` / `transaction` / `auth` / `admin` などドメインごとの分割ができている。
- 共通基盤は `common`（exception, error, response）、外部連携は `integration` に分かれており、責務の分離は明確。

### 2.2 セキュリティフィルタチェーンとパス設計（要確認）

**現状**

- **Order 2（API 用）**: `securityMatcher("/api/**", "/auth/**", "/community/**", "/orders/**")` → JWT、stateless。
- **Order 3（Web 用）**: `securityMatcher("/**")` → フォームログイン、セッション。

**問題**

- `UserController` は `@RequestMapping("/user")` のため、エンドポイントは `/user/me`, `/user/me/profile-image` など。
- これらは **API 用チェーンのマッチャに含まれていない**ため、実際に適用されるのは **Web 用チェーン** になる。
- その結果、`AuthorizationConfig.configureApi()` 内の `.requestMatchers("/user/me/**").hasRole("USER")` は **一度も使われていない**。
- SPA が JWT で `GET /user/me` を呼ぶ想定であれば、現状ではセッション認証が要求され、JWT だけでは 401 になる可能性がある。

**推奨**

- JWT で保護したいユーザー API は、次のいずれかに揃える。
  - **A**: `UserController` のベースパスを `/api/user` に変更し、API 用チェーンに含める。
  - **B**: API 用チェーンの `securityMatcher` に `"/user/**"` を追加し、`/user/me` なども JWT で保護する。
- 意図が「Web（Thymeleaf）のみで `/user/me` を使う」であれば、その旨をコメントまたはドキュメントで明示するとよい。

### 2.3 CORS の適用範囲

**場所:** `CorsConfig.java`

```java
source.registerCorsConfiguration("/api/**", config);
```

- 設定が **`/api/**` のみ** に登録されている。
- `Authorization: Bearer` で呼ぶ `/auth/**`（ログイン・リフレッシュ）や `/user/**` を同一オリジン以外のフロント（例: localhost:3000）から呼ぶ場合、**CORS が適用されずブラウザでブロック**される可能性がある。

**推奨**

- SPA から呼ぶパスをすべてカバーするよう、例えば `/api/**`, `/auth/**`, `/user/**`, `/orders/**` など必要なパスに同じ CORS 設定を `registerCorsConfiguration` で追加するか、`/**` で共通設定を適用する。

## 3. 例外設計・エラーハンドリング

### 3.1 UserService の IllegalArgumentException（要修正）

**場所:** `UserService.java`

- `getRequired`, `updateProfile`, `updateAddress` などで「ユーザーが見つからない」場合に  
  `new IllegalArgumentException("User not found: " + userId)` を投げている。
- `GlobalExceptionHandler` がハンドリングするのは **BusinessException とそのサブクラスのみ** のため、  
  **API では 500 Internal Server Error** となり、クライアントには 404 で返すべきケースが 500 になる。

**推奨**

- リソース不存在は `NotFoundBusinessException.of(ResourceType.USER)` に統一する。
- 既に `updateProfileImage` 内では `NotFoundBusinessException` を使用しているため、他メソッドも同様に揃える。

```java
// 例
.orElseThrow(() -> NotFoundBusinessException.of(ResourceType.USER));
```

### 3.2 UserProfileQueryService.getMe の orElseThrow()

**場所:** `UserProfileQueryService.getMe()`

```java
UserEntity entity = userRepository.findById(userId).orElseThrow();
```

- `getRequired(userId)` の直後に同じ `userId` で `findById` しているため、実質的には必ず存在するが、  
  **契約として「存在しない場合」を明示していない**。
- 将来的に `getRequired` の実装が変わった場合、`NoSuchElementException` がそのまま伝播し、API が 500 になる。

**推奨**

- 意図を明確にするため、  
  `orElseThrow(() -> NotFoundBusinessException.of(ResourceType.USER))` のようにビジネス例外に統一するか、  
  取得は一度だけにして `getRequired` の戻り値（ドメイン）とエンティティの両方が必要な場合は、`getRequired` 側でエンティティも返す設計を検討する。

### 3.3 その他の非 BusinessException

- `User.java` の `requireNonNull` 系で `IllegalArgumentException`、  
  `UserService.updateProfileImage` 内の「Original filename is null」「File extension not found」で `IllegalArgumentException` を使用。
- これらは主に**バリデーション・不正引数**なので、  
  - コントローラで `@Valid` を徹底して防ぐ、  
  - またはサービス層で `ValidationBusinessException` に変換し、API では 400 で返す、  
  のどちらかに揃えると、実務上は扱いやすい。

### 3.4 GlobalExceptionHandler のスコープ（設計として妥当）

- 意図的に **BusinessException のみ** ハンドリングし、それ以外は Spring デフォルトに任せているのは合理的。
- 本番では NPE や `IllegalArgumentException` は 500/400 として返るため、**ログ・APM でスタックトレースを追えるようにしておく**ことが前提となる。

## 4. トランザクション・一貫性

### 4.1 読み取り専用トランザクション（良好）

- `OrderQueryService`, `ItemQueryServiceImpl`, `ProductListService`, `UserProfileQueryService` など、  
  参照のみのメソッドに `@Transactional(readOnly = true)` が付いており、読み取り最適化と意図の表明ができている。

### 4.2 書き込みメソッドの readOnly（問題なし）

- `OrderService.recordOrderPaid` は `@Transactional(readOnly = true)` だが、  
  メソッド内では **DB 更新は行わず通知送信のみ** のため、readOnly で妥当。

### 4.3 複数リソースをまたぐ一貫性（ListingServiceImpl）

**場所:** `ListingServiceImpl.createItem`

- 商品作成 → 画像アップロード → AI モデレーション と、DB と S3・外部 API が混在している。
- 画像アップロード後にモデレーションで例外が出ても、**商品と画像はすでに永続化済み**で、ロールバックは DB 分のみ。
- ドキュメントの「違反時のみDBに記録、出品は成功させる」という方針と一致しているならそのままでよいが、  
  **「画像アップロード失敗時は商品も作成しない」** という仕様であれば、トランザクション境界と S3 のロールバック（削除）の検討が必要。

## 5. API 設計・バリデーション

### 5.1 入力バリデーション（既存レビューとの関係）

- 第二弾で指摘の **RegisterForm.isPasswordMatch()** の論理逆転は、実務上も **早めに修正** する価値が高い。
- 管理者向けの displayName / email の長さ制限（サーバー側）も、DB 制約と合わせて入れておくと安全。

### 5.2 OrderQueryService.getOrderDetail の scope と getMyOrders

- `getMyOrders(userId, scope)` の `scope` は **"seller" / それ以外** で分岐しているが、  
  不正な文字列が来ても「BUYER」として扱われるだけなので、仕様として許容できる。
- 厳密にする場合は、enum または `"seller".equals(scope) ? ... : "buyer"` のように取りうる値を明示するとよい。

### 5.3 エラーレスポンスの統一（良好）

- `ErrorCode` + `ErrorResponse` + `GlobalExceptionHandler` により、API のエラー形式が統一されている。
- メッセージの国際化（MessageSource）も組み込まれており、実務的に十分な水準。

## 6. テスト・品質保証

### 6.1 テストの不足（要対応）

- **現状:** `FleaMarketAppApplicationTests` の context load のみで、実質的な単体・統合テストがない。
- **リスク:** リファクタやバグ修正時のリグレッション検知が難しく、本番障害につながりやすい。

**推奨（優先度の例）**

1. **単体テスト**
   - ドメインロジック: `Order` の状態遷移（confirmPurchase, ship, complete, cancel）など。
   - サービス: `OrderService`, `ReviewService` の主要シナリオ（モックでリポジトリを差し替え）。
   - 例外: `OrderStatus.fromString` の null/不正値、`StripeWebhookVerifier` の署名失敗など。
2. **統合テスト**
   - 認証: ログイン → アクセストークン取得 → 保護された API の呼び出し。
   - 注文フロー: 作成 → 支払い確認 → 発送 → 受け取り確認（必要なら Testcontainers で DB）。
3. **Webhook**
   - 署名あり/なし、不正 payload で期待どおり 400/401/503 になることの確認。

## 7. 運用・観測性

### 7.1 ログ

- ビジネス例外は `GlobalExceptionHandler` で 5xx のとき `log.error(..., ex)`、4xx のとき `log.warn` と分かれており良い。
- S3 アップロード失敗、Webhook の orderId 不正など、重要な不具合はログに残るようになっている。

### 7.2 機密情報

- パスワード・トークンをログに出している箇所は見当たらない（既存レビューと同様）。

### 7.3 本番設定（既存レビューとの関係）

- セッション Cookie の **secure / sameSite** は本番プロファイルで明示することが推奨される（第二弾の通り）。
- Stripe Webhook の **webhookSecret** が null/blank のときの 503 対応は、`StripeWebhookVerifier` で実装済み。

## 10. まとめ

- **強み:** ドメイン分離、エラーコード・例外の設計、セキュリティ（JWT/Webhook/CSRF/リダイレクト）の意識は実務レベルで十分に感じられる。
- **改善で効果が大きいところ:**  
  - **API の例外を BusinessException に統一**して 4xx/5xx を意図どおりに返すこと。  
  - **認証・CORS のパス設計**を「SPA がどの URL をどう認証するか」に合わせて明確にすること。  
  - **テスト**を少しずつでも入れて、変更の安全性を担保すること。  

既存の第一弾・第二弾の指摘とあわせて対応すると、本番運用と保守性がさらに安定します。
