## 2. アーキテクチャ・設計

### 良い点

- **ドメインとエンティティの分離**: `Order` / `OrderEntity`、`User` / `UserEntity`、`Listing` など、状態遷移やビジネスルールをドメインに集約し、永続化は Entity に任せる構成になっている。
- **モジュール分割**: `admin` / `auth` / `catalog` / `listing` / `transaction` / `user` / `engagement` など機能単位でパッケージが分かれており、責務が把握しやすい。
- **ポート/アダプタの意識**: AWS（Comprehend, Rekognition, Fraud Detector）を `*Port` / `*Adapter` で抽象化し、テスト時のモックがしやすい。
- **イベント・共通基盤**: `DomainEvent` / `EventPublisher`、`ErrorCode`、`ApiResponse` / `ErrorResponse` など共通の契約が定義されている。

### 要検討・軽微

- **Controller のベースパス**: `UserController` が `/api/user`、`ChatController` が `/orders` など、REST のリソース階層が API ツリー上でややばらついている。将来的に `/api/orders/**` に寄せるか、現状で「Web 用 / API 用」をドキュメントで明示するとよい。
- **DTO の配置**: コントローラ直下の `dto` とサービス直下の `dto` が混在。「コントローラは API 契約、サービスはアプリケーション契約」のように役割を分けておくと、将来の API バージョン切り替えがしやすい。

## 3. セキュリティ

### 良い点

- **認証・認可の分離**: 管理者ログイン（Order 1）、API 用 JWT（Order 2）、Web セッション（Order 3）の 3 本のフィルタチェーンで、役割が明確。
- **CSRF**: Web は有効、Webhook は `/webhooks/**` のみ除外。API は stateless のため CSRF 無効で妥当。
- **JWT**: アクセストークン・リフレッシュトークンが実装され、秘密鍵は環境変数 `APP_JWT_SECRET` で指定する前提。
- **オープンリダイレクト対策**: 未認証時の `returnUrl` で相対パスのみ許可（`//` で始まる絶対URLを排除）。
- **Webhook**: Stripe の署名検証（`StripeWebhookVerifier`）で改ざん・なりすましを防止。
- **CORS**: `/api/**`, `/auth/**`, `/user/**`, `/orders/**`, `/community/**` に設定が適用されており、SPA からの呼び出しをカバーしている。
- **ユーザー API**: `UserController` が `/api/user` のため、API 用チェーン（`/api/**`）で保護され、JWT でアクセス可能。

### 要確認・推奨

- **本番の Cookie**: 本番プロファイルで `server.servlet.session.cookie.secure=true`、`sameSite=Strict`（または Lax）の明示を推奨。
- **JWT の有効期限**: `app.jwt.access-token-expiration=15m` は妥当。リフレッシュトークンのローテーションや無効化リストの有無は要件に応じて検討するとよい。

## 4. 例外設計・エラーハンドリング

### 良い点

- **ErrorCode と HTTP ステータスの対応**: 各 `ErrorCode` が `HttpStatus` を持ち、`GlobalExceptionHandler` で一括マッピングされている。
- **BusinessException 系**: `NotFoundBusinessException`、`ValidationBusinessException`、`AccessDeniedBusinessException` などが `ResourceType` と組み合わせて使い分けられている。
- **API/Web の振り分け**: `Accept: text/html` のときは HTML エラーページ、それ以外は JSON を返す設計で、同一ハンドラで両対応している。
- **UserService**: `getRequired`、`updateProfile`、`updateAddress`、`submitVerification`、`updateProfileImage` で `NotFoundBusinessException` / `ValidationBusinessException` を利用しており、API が 404/400 を返すようになっている。
- **UserRankService**: `loadRank` で `NotFoundBusinessException.of(ResourceType.RANK)` を使用。

### 要対応・注意

- **ドメイン層の IllegalArgumentException**: `User.requireText()`、`Listing` のバリデーションなどで `IllegalArgumentException` を投げている。コントローラで `@Valid` を徹底していれば多くは防げるが、サービス層でドメインを直接触る経路では 500 になる可能性がある。サービス層で catch して `ValidationBusinessException` に変換するか、ドメインの契約を「呼び出し元が事前に検証すること」と Javadoc で明記するとよい。
- **UserProfileQueryService.getMe**: `userRepository.findById(userId).orElseThrow()` のように無引数 `orElseThrow()` を使っている場合、存在しないと `NoSuchElementException` で 500 になる。`NotFoundBusinessException.of(ResourceType.USER)` に統一すると安全。
- **ProductPageController**: `IllegalArgumentException` を catch してフォーム用のエラー表示にしている。API と Web で経路が分かれているため、現状でも致命的ではないが、メッセージの国際化や ErrorCode との対応を揃えると保守しやすい。
- **GlobalExceptionHandler**: 現状は `BusinessException` のみハンドリングし、それ以外は Spring デフォルトに委譲する方針で一貫している。5xx のログ・監視は運用でカバーするとよい。

## 5. トランザクション・一貫性

### 良い点

- **読み取り専用トランザクション**: `OrderQueryService`、`ItemQueryServiceImpl`、`UserProfileQueryService`、`ChatService.listMessages` などで `@Transactional(readOnly = true)` が付与されている。
- **書き込みの境界**: 注文の状態変更（`confirmPurchase`、`ship`、`complete`、`cancel`）は 1 トランザクション内で Entity の更新まで完結している。
- **ListingServiceImpl**: 商品作成 → 画像アップロード → AI モデレーションの順。モデレーション失敗時は「違反のみ記録・出品は成功」という仕様で、トランザクション境界と一致している。

### 注意点

- **S3 と DB の整合性**: 画像アップロード成功後に DB 更新で失敗した場合、S3 にゴミが残る。許容するか、補償トランザクション（S3 削除）や「DB 先に書いてから S3」などの設計は要件次第で検討の余地あり。
- **recordOrderPaid**: 既に PAID の場合は早期 return しており、二重送信防止になっている。

## 6. API 設計・一貫性

### 良い点

- **REST の活用**: `GET` で取得、`POST` で作成、`ResponseEntity` で 201 Created + Location を返すなど、一般的な慣習に沿っている。
- **バリデーション**: `@Valid` と Bean Validation を利用。`BoardController` の `@Min(1) @Max(100)` など、入力制約が明示されている。
- **認証の取得**: `SecurityUtil.getCurrentUserId()` でユーザーID を取得し、リクエストボディにユーザーID を持たせない設計（ChatController のコメントにも記載）は正しい。

### 要改善

- **レスポンス形式の統一**: 
  - `BoardController` は `ApiResponse.success(posts)` で `{ "success": true, "data": ... }` を返している。
  - `ChatController#listMessages` は `List<OrderMessageEntity>` をそのまま返しており、`ApiResponse` でラップしていない。
  - 他 API でも「常に ApiResponse でラップする」「データのみ返す」のどちらかに揃えると、フロントやドキュメント生成がしやすい。
- **エンティティの直接公開**: `OrderMessageEntity` をそのまま返すと、スキーマ変更が API の破壊的変更になりやすい。可能であれば DTO（例: `ChatMessageResponse`）を用意し、必要なフィールドだけ返すとよい。
- **ページネーション**: 一覧系（掲示板投稿、メッセージ一覧など）で `limit` はあるが、`offset` や cursor によるページングが無い。件数増加時に負荷・UX の観点で検討の余地あり。

## 7. テスト

### 良い点

- **Testcontainers**: PostgreSQL を使用した統合テスト環境が用意されている。
- **IntegrationTestBase**: 認証ヘルパー（`obtainAccessToken`、`authHeaders`）と AWS/外部サービスのモックが共通化されている。
- **認証・Webhook の統合テスト**: `AuthIntegrationTests`（ログイン成功/失敗、管理者ログイン）、`StripeWebhookIntegrationTests`、`UserApiIntegrationTests` など、重要な経路がテストされている。

### 要改善

- **単体テスト**: ドメイン（`Order` の状態遷移、`OrderStatus.fromString`）、主要サービス（注文フロー、ユーザー更新）、バリデーター（`PasswordPolicy`、`EmailValidator`）などの単体テストがほとんどない。リファクタ時の安全性を高めるには、まずドメインとサービス層の単体テストを増やすと効果が大きい。
- **カバレッジ**: 現状は「コンテキストロード + 一部統合」が中心のため、カバレッジ計測を有効にし、重要パス（注文、決済、認証）を目標値として設定するとよい。
- **異常系**: 署名不正の Webhook、不正な状態遷移、存在しない ID での取得など、4xx/5xx が期待どおり返ることを断言するテストがあると安心。

## 8. 保守性・ドキュメント

### 良い点

- **README**: プロジェクト体制、主要機能、技術スタック、ディレクトリ構成が整理されている。
- **docs**: Flyway マイグレーション、AWS デプロイ時の調整、既存のコードレビュー報告などが残っており、引き継ぎやレビュー追跡がしやすい。
- **Javadoc**: `GlobalExceptionHandler`、`ErrorCode`、主要なサービス・ドメインに説明が書かれており、意図が読み取りやすい。
- **Flyway**: V1（スキーマ）、V2（シード）でマイグレーションが管理され、`spring.jpa.hibernate.ddl-auto=none` でスキーマの一元管理ができている。

### 軽微

- **DateTimeUtil**: 以前指摘されていた typo（"ust" → "must"）は修正済み。
- **pom.xml**: Spring Boot 4.0.1、Java 17、BOM で AWS SDK のバージョン管理など、依存関係は整理されている。本番で使わない Flyway の `dev_migration` はプロファイルで locations を切り替えているとよい。

## 9. 改善推奨一覧（優先度順）

| 優先度 | 項目 | 内容 |
|--------|------|------|
| 高 | API レスポンス形式の統一 | 一覧・取得系を `ApiResponse<T>` でラップするか、全 API で「生データ」に揃えるか方針を決め、ChatController 等を合わせる。 |
| 高 | 一覧 API のページネーション | 掲示板・メッセージ一覧に offset/limit または cursor を導入し、最大件数上限を明示する。 |
| 中 | ドメインの IAE と 500 防止 | サービス層でドメインの `IllegalArgumentException` を catch し、`ValidationBusinessException` に変換するか、コントローラの `@Valid` で防ぎ切る。 |
| 中 | UserProfileQueryService.getMe | `orElseThrow()` を `orElseThrow(() -> NotFoundBusinessException.of(ResourceType.USER))` に変更。 |
| 中 | 単体テストの追加 | Order/Listing/User のドメイン、OrderService/ChatService/UserService の主要シナリオ、StripeWebhookVerifier の署名検証の単体テストを追加。 |
| 低 | エンティティの直接返却の廃止 | 必要に応じて `OrderMessageEntity` → `ChatMessageResponse` など DTO を導入し、API 契約を安定させる。 |
| 低 | 本番セキュリティ設定 | セッション Cookie の secure / sameSite を本番プロファイルで明示。 |

## 10. まとめ

- **強み**: ドメインとエンティティの分離、ErrorCode と GlobalExceptionHandler によるエラー契約の統一、セキュリティ（JWT/CSRF/Webhook/オープンリダイレクト）の考慮、CORS と認可パスの整理、Testcontainers と統合テスト基盤が実務レベルでよく整っている。
- **スコア 76 の内訳**: 設計・セキュリティは高水準。例外設計はほぼ統一されているが、ドメインの IAE と一部 orElseThrow() で改善の余地あり。API のレスポンス形式とページネーションの統一、テストの拡充で 80 点台後半を狙える。
- 上記の改善推奨を優先度に従って対応すると、本番運用と長期保守の安定性がさらに向上する。
